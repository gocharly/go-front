# Backend

## Назначение

Backend отвечает за серверную логику приложения, работу с данными, авторизацию, внешние сервисы и выполнение операций, которые не должны выполняться непосредственно на клиенте.

Backend должен быть:

* понятным;
* предсказуемым;
* безопасным;
* тестируемым;
* устойчивым к ошибкам;
* соответствующим реальному размеру проекта.

Не создавать сложную серверную архитектуру без необходимости.

---

## Перед созданием backend

Определить:

* какие данные принимает система;
* какие данные возвращает;
* какие операции выполняются;
* где хранятся данные;
* какие пользователи имеют доступ;
* какие внешние API используются;
* какие операции требуют авторизации;
* какие операции могут выполняться долго;
* какие данные являются чувствительными;
* какие ошибки могут возникнуть.

После этого определить минимальную структуру backend.

---

## Основная структура

Типовая последовательность:

```text
Request
↓
Route
↓
Validation
↓
Authentication / Authorization
↓
Business logic
↓
Database / External API
↓
Response
```

Каждый этап должен иметь понятную ответственность.

Не помещать всю обработку запроса в один обработчик.

---

## Routes

Routes отвечают за определение endpoint и передачу запроса дальше.

Например:

```text
GET    /users
GET    /users/:id
POST   /users
PATCH  /users/:id
DELETE /users/:id
```

Route не должен содержать всю бизнес-логику приложения.

Плохо:

```text
route
 ├── validation
 ├── database queries
 ├── calculations
 ├── external API
 ├── permissions
 └── response
```

Предпочтительно:

```text
route
↓
service
↓
repository / integration
```

---

## Validation

Входные данные необходимо проверять до выполнения основной логики.

Проверять:

* обязательные поля;
* типы;
* формат;
* диапазоны;
* допустимые значения;
* размеры данных;
* связанные ограничения.

Нельзя доверять данным только потому, что клиент уже выполнил проверку.

Frontend validation улучшает интерфейс.

Backend validation обеспечивает корректность и безопасность сервера.

---

## Business Logic

Основные правила приложения должны находиться в понятном месте.

Например:

```text
CreateOrder
CalculateOrderTotal
CancelOrder
RegisterUser
UpdateProfile
ProcessPayment
```

Названия должны отражать реальное действие.

Не создавать универсальный `Manager`, который содержит всю бизнес-логику проекта.

Если сервис начинает выполнять слишком много разных задач — разделить его по ответственности.

---

## Database

Работу с базой отделять от бизнес-логики, когда это улучшает структуру.

Например:

```text
Service
↓
Repository
↓
Database
```

Repository отвечает за получение и изменение данных.

Service отвечает за правила приложения.

Не помещать бизнес-правила непосредственно в SQL-запросы без необходимости.

Не дублировать одинаковые запросы по всему проекту.

---

## Database Schema

Перед созданием таблиц определить сущности и связи.

Например:

```text
users
products
orders
order_items
payments
```

Не создавать таблицы заранее «на будущее».

Структура базы должна соответствовать реальным данным приложения.

При изменении схемы использовать миграции.

Не изменять production-базу вручную, если проект использует систему миграций.

---

## Transactions

Использовать транзакции там, где несколько операций должны выполниться как единое действие.

Например:

```text
Create order
+
Create order items
+
Update balance
```

Если одна часть операции не выполнилась, состояние базы не должно остаться частично изменённым.

Не использовать транзакции вокруг операций, которым они не нужны.

---

## Authentication

Разделять:

**Authentication** — кто пользователь.

**Authorization** — что пользователь может делать.

Не смешивать эти понятия в одной функции.

Проверка доступа должна выполняться на backend.

Нельзя считать пользователя авторизованным только потому, что frontend показывает ему соответствующий интерфейс.

---

## Passwords и секреты

Пароли пользователей нельзя хранить в открытом виде.

Использовать предназначенные для этого алгоритмы хеширования паролей.

Секреты не хранить:

```text
в исходном коде
в Git
в frontend
в публичных конфигурационных файлах
```

Использовать переменные окружения или подходящее защищённое хранилище.

Не записывать токены, пароли и другие секреты в логи.

---

## API

API должен иметь понятный контракт.

Определить:

* endpoint;
* HTTP method;
* параметры;
* тело запроса;
* формат ответа;
* ошибки;
* авторизацию.

Пример:

```text
POST /api/orders
```

```json
{
    "items": [...]
}
```

```json
{
    "orderId": "...",
    "total": 1200
}
```

Не менять формат API без учёта существующих клиентов.

---

## Ошибки

Ошибки должны обрабатываться предсказуемо.

Разделять:

* ошибка пользователя;
* ошибка авторизации;
* отсутствие ресурса;
* конфликт;
* ошибка внешнего сервиса;
* внутренняя ошибка сервера.

Не возвращать пользователю внутренние stack trace, SQL-запросы, секреты или технические детали.

Внутри системы сохранять достаточно информации для диагностики.

---

## Внешние API

Внешние сервисы подключать через отдельные интеграции.

Например:

```text
services/
integrations/
    telegram/
    discord/
    payments/
    storage/
```

Не распространять детали конкретного внешнего API по всему проекту.

Если API изменится, изменения должны по возможности ограничиваться его интеграцией.

---

## Платежи

Платёжные операции должны выполняться через надёжный платёжный сервис.

Backend должен:

* создавать платёж;
* проверять статус;
* обрабатывать callback/webhook;
* проверять подлинность webhook;
* фиксировать результат операции;
* предотвращать повторную обработку одной оплаты.

Нельзя считать платёж успешным только на основании данных frontend.

---

## Webhooks

Webhook должен:

1. Проверить источник запроса.
2. Проверить подпись или другой механизм подтверждения.
3. Проверить данные.
4. Обработать событие.
5. Зафиксировать результат.
6. Корректно ответить сервису.

Обработчики webhook должны учитывать повторную доставку одного события.

Операции, которые нельзя выполнять дважды, должны быть защищены от повторной обработки.

---

## Долгие операции

Если операция выполняется долго, не удерживать обычный HTTP-запрос без необходимости.

Например:

```text
Request
↓
Create task
↓
Queue
↓
Worker
↓
Result
```

Использовать фоновые задачи только тогда, когда они действительно нужны.

Не добавлять очередь и worker для простой операции, которая выполняется быстро.

---

## Cache

Кэш использовать только там, где он действительно решает проблему.

Перед добавлением кэша определить:

* что кэшируется;
* сколько живут данные;
* когда они становятся устаревшими;
* как происходит очистка;
* что произойдёт при отсутствии кэша.

Кэш не должен становиться единственным источником критически важных данных.

---

## Логирование

Логи должны помогать находить реальные проблемы.

Записывать:

* ошибки;
* важные события;
* идентификаторы операций;
* время выполнения;
* необходимые технические параметры.

Не записывать:

* пароли;
* токены;
* данные банковских карт;
* секретные ключи;
* чувствительные данные без необходимости.

Не превращать логи в поток бесполезных сообщений.

---

## Конфигурация

Конфигурация должна быть отделена от исходного кода.

Например:

```text
DATABASE_URL
API_KEY
BOT_TOKEN
PORT
APP_ENV
```

Разделять настройки окружения:

```text
development
staging
production
```

если проект действительно использует несколько окружений.

Не создавать сложную систему конфигурации для маленького проекта.

---

## Безопасность

Backend должен учитывать:

* проверку входных данных;
* авторизацию;
* управление доступом;
* защиту секретов;
* SQL injection;
* XSS при работе с пользовательскими данными;
* CSRF там, где это применимо;
* rate limiting;
* безопасную обработку файлов;
* ограничения размера запросов;
* таймауты;
* безопасные HTTP-заголовки;
* обновление зависимостей.

Не считать frontend частью системы безопасности.

Все критические проверки должны выполняться на сервере.

---

## Производительность

Сначала реализовать корректную систему.

Затем измерить реальные узкие места.

Не оптимизировать код без причины.

Перед оптимизацией определить:

```text
Что медленно?
Почему медленно?
Где находится узкое место?
Как измеряется улучшение?
```

Не добавлять кэш, очереди, микросервисы или дополнительные базы данных только ради предполагаемой производительности.

---

## Масштабирование

Не проектировать распределённую систему заранее.

Начинать с простой архитектуры.

Переходить к более сложной структуре только при появлении реальной причины:

```text
Single application
↓
Load separation
↓
Background workers
↓
Caching
↓
Separate services
```

Каждый следующий уровень должен решать конкретную проблему.

---

## Микросервисы

Не использовать микросервисы по умолчанию.

Для большинства небольших и средних проектов достаточно одного backend-приложения с хорошо разделёнными модулями.

Выносить отдельный сервис, когда:

* область действительно независима;
* её необходимо масштабировать отдельно;
* она имеет отдельный жизненный цикл;
* разделение реально уменьшает сложность.

Не создавать микросервис для каждой функции.

---

## Тестирование

Проверять backend минимум на:

* основной успешный сценарий;
* неправильные входные данные;
* отсутствие авторизации;
* отсутствие прав;
* несуществующий ресурс;
* ошибки базы данных;
* ошибки внешнего API;
* повторные запросы;
* пограничные значения.

Критическую бизнес-логику покрывать автоматическими тестами.

Не писать тесты только ради количества.

---

## Структура проекта

Структура зависит от размера приложения.

Небольшой проект:

```text
src/
├── routes/
├── services/
├── database/
└── config/
```

Средний проект:

```text
src/
├── modules/
│   ├── users/
│   ├── orders/
│   └── products/
├── integrations/
├── database/
└── config/
```

Большой проект может использовать более строгую модульную структуру.

Не копировать структуру большого проекта в маленький.

---

## Что не делать

Не:

* помещать всю логику в routes;
* создавать один огромный `service`;
* создавать универсальный `utils`;
* дублировать запросы к базе;
* хранить секреты в коде;
* доверять frontend-проверкам;
* возвращать внутренние ошибки пользователю;
* создавать микросервисы без причины;
* добавлять Redis без реальной необходимости;
* добавлять очередь без долгих или массовых задач;
* создавать несколько баз данных без необходимости;
* оптимизировать до появления проблемы;
* усложнять API без требования;
* создавать отдельный слой только ради красивой структуры.

---

## Проверка backend перед завершением

Перед завершением проверить:

* Корректно ли обрабатываются входные данные?
* Проверяется ли авторизация?
* Проверяются ли права доступа?
* Нет ли секретов в коде?
* Корректно ли обрабатываются ошибки?
* Не дублируется ли бизнес-логика?
* Понятно ли назначение модулей?
* Не перегружены ли handlers/routes?
* Корректно ли работают транзакции?
* Обрабатываются ли повторные запросы?
* Не раскрываются ли внутренние данные?
* Нет ли ненужной инфраструктуры?
* Проверены ли основные сценарии и ошибки?

### Основной принцип

**Backend должен решать задачу максимально простой и надёжной структурой, которая соответствует реальным требованиям проекта.**

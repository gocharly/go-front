# Диагностика доступности веб-сайтов и сетевой связности

Модульный регламент проверки работоспособности веб-ресурсов, выявления региональных сетевых сбоев, блокировок ТСПУ/DPI и мониторинга доступности.

---

## 1. Базовый протокол действий агента при инцидентах

Когда поступает жалоба вида "сайт не открывается", "ошибка 502", "не грузится из определенного региона":

```text
1. Локализация и воспроизведение
   ├── Проверка веб-сервера (процесс, порты, логи)
   └── Проверка DNS и SSL-сертификата
              ↓
2. Глобальная и региональная проверка
   ├── Проверка через внешние распределенные ноды (check-host.net API)
   └── Сравнение ответов из СНГ/РФ и Европы/США
              ↓
3. Определение первопричины (Root Cause)
   ├── Сбой сервиса / Nginx / приложения
   ├── Ошибка конфигурации DNS / SSL
   └── Блокировка подсети хостинга провайдером / ТСПУ
              ↓
4. Обязательный доклад пользователю и согласование
   └── Фиксация проблемы, причин и плана -> Ожидание подтверждения -> Правка
```

Категорически запрещено начинать менять конфигурацию веб-сервера или код до выявления точной первопричины и согласования с пользователем.

## 2. Сервисы для проверки доступности сайтов

### 2.1. Check-Host.net (Приоритетный инструмент)
Предоставляет как веб-интерфейс, так и REST API для консольной проверки из десятков независимых точек мира (включая ноды в РФ, ЕС, США, Азии).

#### Проверка через API из терминала:
```bash
# 1. Запуск HTTP-проверки (возвращает request_id)
curl -s "https://check-host.net/check-http?host=https://example.com&max_nodes=10" -H "Accept: application/json"

# 2. Получение результатов по request_id (через 3-5 секунд после запуска):
curl -s "https://check-host.net/check-result/REQUEST_ID" -H "Accept: application/json"

# 3. Проверка Ping:
curl -s "https://check-host.net/check-ping?host=example.com&max_nodes=10" -H "Accept: application/json"

# 4. Проверка TCP-порта (например, 443 или 80):
curl -s "https://check-host.net/check-tcp?host=example.com:443&max_nodes=10" -H "Accept: application/json"
```

Коды нод для проверки доступности из РФ: `ru1.node.check-host.net`, `ru2.node.check-host.net`, `ru3.node.check-host.net`.

### 2.2. Ping-Admin (ping-admin.ru / ping-admin.com)
- Сервис распределенного мониторинга и мгновенной проверки доступности сайтов и серверов.
- Содержит крупнейшую сеть зондирующих станций в городах России, Беларуси, Казахстана, Европы и США.
- Позволяет выявлять точечные проблемы конкретных региональных провайдеров (Ростелеком, МТС, Мегафон, Дом.ру).

### 2.3. Host-Tracker (host-tracker.com)
- Международный сервис глобальной проверки времени отклика, HTTP/HTTPS статусов и трассировки маршрутов со 140+ серверов.

### 2.4. UptimeRobot (uptimerobot.com)
- Платформа для постоянного периодического мониторинга HTTP(S), портов и SSL с уведомлениями в Telegram и Webhook.

### 2.5. 2IP (2ip.ru / 2ip.io)
- Экспресс-проверка открытых портов (`2ip.ru/check-port/`).
- Проверка доступности сайта из сети Интернет (`2ip.ru/site-availability/`).
- Проверка IP, геолокации и провайдера хостинга.

## 3. Консольные команды для локальной и удаленной диагностики

### 3.1. Проверка DNS-резолвинга через независимые апстримы
Если сайт доступен в одной стране, но не резолвится в другой:
```bash
# Проверка через Yandex DNS (Россия)
dig @77.88.8.8 example.com +short

# Проверка через Cloudflare DNS (глобальный)
dig @1.1.1.1 example.com +short

# Проверка через Google DNS
dig @8.8.8.8 example.com +short

# Проверка через системный резолвер
nslookup example.com
```

Если Yandex DNS отдает IP, а Cloudflare другой или пустой - проблема в кэше зоны, делегировании NS-записей или сбое авторитетных серверов.

### 3.2. Проверка HTTP/HTTPS ответов и цепочки редиректов
```bash
# Проверка HTTP ответа и 301 редиректа на HTTPS:
curl -s -I "http://example.com"

# Проверка HTTPS ответа с деталями хэндшейка и заголовков:
curl -s -Iv "https://example.com" -o /dev/null

# Проверка времени ответа сервера:
curl -o /dev/null -s -w 'Lookup: %{time_namelookup}s | Connect: %{time_connect}s | TLS: %{time_appconnect}s | Total: %{time_total}s\n' "https://example.com"
```

### 3.3. Проверка SSL/TLS сертификата и хэндшейка
```bash
# Проверка валидности сертификата и цепочки доверия:
openssl s_client -connect example.com:443 -servername example.com < /dev/null 2>/dev/null | openssl x509 -noout -dates -subject -issuer
```

### 3.4. Проверка на целевом сервере
```bash
# Слушающие порты (80, 443, порты бэкенда):
ss -tulpn | grep -E ':80|:443'

# Статус веб-сервера (Nginx / Caddy):
systemctl status nginx
nginx -t

# Логи последних ошибок:
tail -n 50 /var/log/nginx/error.log
```

## 4. Диагностика региональных блокировок и ТСПУ

### Симптомы блокировки подсети хостинга ТСПУ/РКН:
1. Зарубежные ноды (Германия, Финляндия, США) отдают `200 OK` за 50-150мс.
2. Ноды из РФ (`ru1`, `ru2` в `check-host.net`) зависают по таймауту (`Connection timed out` или сброс `Connection reset by peer`).
3. DNS при этом резолвит IP адрес корректно.

### Причина:
Прямой IP-адрес зарубежного хостинга (Hetzner, OVH, DigitalOcean, Linode) попал под веерные блокировки или фильтрацию ТСПУ по маске протокола/подсети.

### Решение:
1. Подключение Anycast CDN (Cloudflare Proxy): скрывает исходный IP европейского датацентра за распределенными IP-адресами Cloudflare.
2. Смена исходящего IP на сервере или перенос входящего прокси на хостинг, не затронутый блокировками.
3. Проверка статуса IP в реестрах блокировок.

## 5. Чек-лист перед докладом пользователю

Перед отправкой сообщения с результатами проверки:
- [ ] Проверены минимум 3 географические точки (ЕС, США, РФ) через `check-host.net`.
- [ ] Проверен локальный статус веб-сервера и лог ошибок.
- [ ] Проверен DNS-резолвинг на независимых серверах.
- [ ] Проверен SSL-сертификат на дату истечения.
- [ ] Точно сформулирована первопричина (код, конфиг, сеть, сертификат или блокировка провайдера).
- [ ] Подготовлен конкретный план действий без самодеятельности.

# Упрощение кода и организация функций

## Цель

Код должен оставаться простым для чтения даже после добавления большого количества функциональности.

При разработке необходимо постоянно проверять:

* можно ли сделать код короче без потери понятности;
* можно ли убрать повторение;
* можно ли дать более точное имя;
* можно ли разделить перегруженную функцию;
* можно ли вынести повторно используемую логику;
* не создаёт ли текущая структура лишнюю сложность.

**Меньше кода — не всегда лучше. Понятнее код — лучше.**

---

## Не писать всё в одном файле

Если файл начинает содержать несколько независимых областей логики, разделить их.

Например, вместо:

```text
app/
└── main.ts
```

где находятся:

```text
авторизация
работа с пользователями
работа с товарами
форматирование
API-запросы
валидация
```

использовать отдельные модули.

---

## Называть файлы по их реальной работе

Название файла должно позволять понять его назначение без открытия файла.

Плохо:

```text
helpers.ts
utils.ts
common.ts
stuff.ts
manager.ts
functions.ts
misc.ts
```

если внутри находятся разные несвязанные функции.

Хорошо:

```text
formatPrice.ts
validateEmail.ts
createOrder.ts
calculateTotal.ts
telegramClient.ts
database.ts
```

или, если функций много:

```text
libs/
├── formatting/
├── validation/
├── payments/
└── telegram/
```

Название должно соответствовать содержимому.

---

## Общие функции

Для функций, которые используются в нескольких частях проекта, можно создавать отдельную директорию:

```text
libs/
├── formatting/
├── validation/
├── dates/
└── api/
```

Например:

```text
libs/
└── formatting/
    ├── formatPrice.ts
    ├── formatDate.ts
    └── formatPhone.ts
```

После этого функции импортируются там, где они необходимы:

```typescript
import { formatPrice } from "@/libs/formatting/formatPrice";
```

Не копировать одну и ту же функцию по разным файлам.

---

## Группировать действительно связанные функции

Если несколько функций работают с одной областью, их можно объединить в модуль:

```text
libs/
└── payments/
    ├── createPayment.ts
    ├── checkPaymentStatus.ts
    └── verifyPaymentWebhook.ts
```

или использовать один файл, если функций немного:

```text
libs/
└── payments.ts
```

Выбор зависит от размера.

Не создавать отдельный файл для каждой функции автоматически.

---

## Когда создавать `libs`

`libs` можно использовать для небольших самостоятельных функций и модулей, которые:

* не относятся к конкретной странице;
* не относятся к конкретному компоненту;
* используются в нескольких местах;
* имеют одну понятную область назначения;
* могут использоваться независимо от основной бизнес-логики.

Например:

```text
libs/
├── formatting/
├── validation/
├── dates/
├── storage/
└── api/
```

Но не превращать `libs` в свалку всего общего кода.

Если функция относится к конкретной бизнес-области, хранить её рядом с этой областью.

Например:

```text
modules/
└── orders/
    ├── createOrder.ts
    ├── cancelOrder.ts
    └── calculateOrderTotal.ts
```

а не:

```text
libs/
└── everything.ts
```

---

## Разделять общую и бизнес-логику

Общие функции:

```typescript
formatPrice()
formatDate()
validateEmail()
parseUrl()
```

могут находиться в `libs`.

Функции, содержащие правила конкретного продукта:

```typescript
calculateOrderTotal()
cancelOrder()
approveRefund()
createProduct()
```

лучше хранить в соответствующем модуле:

```text
modules/
├── orders/
├── products/
├── users/
└── payments/
```

Это позволяет быстро понять, где находится необходимая логика.

---

## Уменьшать размер функций

Если функция выглядит примерно так:

```text
load data
validate data
calculate something
format result
save result
send notification
```

проверить, можно ли разделить её:

```typescript
loadData()
validateData()
calculateResult()
saveResult()
sendNotification()
```

Но не превращать каждый оператор в отдельную функцию.

Разделять только самостоятельные логические операции.

---

## Убирать ненужные промежуточные слои

Не делать:

```text
route
↓
controller
↓
handler
↓
manager
↓
service
↓
processor
↓
repository
```

если каждый слой просто передаёт вызов дальше.

Если слой не добавляет ответственности, его существование необходимо пересмотреть.

Для небольшой задачи может быть достаточно:

```text
route
↓
service
↓
database
```

---

## Повторяющийся код

Если один и тот же код появился несколько раз:

1. Проверить, действительно ли логика одинаковая.
2. Определить её ответственность.
3. Выбрать подходящее место.
4. Вынести её туда.
5. Импортировать там, где она нужна.

Например:

```text
libs/
└── formatting/
    └── formatPrice.ts
```

Вместо копирования `formatPrice()` в пяти разных файлах.

---

## Не создавать универсальные файлы

Не делать:

```text
libs/
├── utils.ts
├── helpers.ts
└── common.ts
```

куда постепенно складывается всё подряд.

Если в файле появляются функции разных назначений, разделить их по областям.

Например:

```text
libs/
├── formatting/
├── validation/
├── dates/
└── storage/
```

---

## Убирать ненужный код

При изменении существующей системы проверять:

* используется ли старый код;
* нужен ли старый импорт;
* нужен ли старый компонент;
* нужен ли старый endpoint;
* не осталась ли старая функция;
* не осталось ли дублирование.

Если код больше не нужен — удалить его.

Не оставлять мёртвый код «на всякий случай».

---

## Не сокращать код в ущерб пониманию

Плохая цель:

> сделать как можно меньше строк.

Правильная цель:

> сделать как можно проще для понимания.

Например, не нужно превращать сложную последовательность действий в одну огромную строку только ради уменьшения количества строк.

Предпочтительнее несколько коротких, понятных операций.

---

## Порядок упрощения

Если код сложный, использовать последовательность:

```text
1. Понять существующую логику
2. Удалить мёртвый код
3. Удалить дублирование
4. Улучшить названия
5. Разделить перегруженные функции
6. Вынести действительно общую логику
7. Разделить несвязанные области
8. Проверить структуру
9. Проверить работу
```

Не начинать с полного переписывания.

---

## Проверка структуры

После создания или изменения кода проверить:

```text
Можно ли понять назначение файла по его названию?
Можно ли понять назначение функции по её названию?
Нет ли в файле несвязанных функций?
Нет ли одинаковой логики в нескольких местах?
Не стал ли libs свалкой функций?
Не создаётся ли слишком много файлов?
Нет ли лишних слоёв между компонентами?
Можно ли удалить часть кода без изменения поведения?
```

---

## Основной принцип

**Каждый файл, функция и модуль должны иметь понятную причину своего существования.**

Если код можно сделать проще без потери функциональности и понятности — упростить.

Если общая функция используется в нескольких местах — вынести её в подходящий общий модуль и импортировать.

Если функция относится к конкретной области продукта — хранить её рядом с этой областью.

Не стремиться к минимальному количеству файлов.

Не стремиться к максимальному количеству модулей.

Стремиться к **понятной структуре, в которой легко найти нужную логику и понять её назначение.**

# Упрощение кода и организация функций

## Цель

Код должен оставаться простым для чтения даже после добавления большого количества функциональности.

**Меньше кода — не всегда лучше. Понятнее код — лучше.**

---

## Не писать всё в одном файле

Если файл содержит несколько независимых областей логики, разделить их на отдельные модули.

---

## Называть файлы по их реальной работе

Название файла должно позволять понять его назначение без открытия файла.

**Запрещены свалки разнородного кода:**
`helpers.ts`, `utils.ts`, `common.ts`, `stuff.ts`, `manager.ts`, `functions.ts`, `misc.ts`.

**Рекомендуется называть по действию:**
`formatPrice.ts`, `validateEmail.ts`, `createOrder.ts`, `calculateTotal.ts`, `telegramClient.ts`, `database.ts`.

Или модульными папками:
`libs/formatting/`, `libs/validation/`, `libs/payments/`, `libs/telegram/`.

---

## Общие функции и директория `libs/`

`libs` используется для небольших самостоятельных функций, которые используются в нескольких местах и не привязаны к конкретной бизнес-сущности.
Бизнес-логику хранить рядом со своими доменами в `modules/orders/`, `modules/products/`.

---

## Убирать ненужные промежуточные слои

Не делать цепочки:
```text
route → controller → handler → manager → service → processor → repository
```
если каждый слой просто передаёт вызов дальше.

Для большинства задач достаточно:
```text
route → service → database
```

---

## Убирать мёртвый код

Удалять неиспользуемые импорты, старые endpoints, компоненты и сиротские функции. Не оставлять мёртвый код «на всякий случай».

---

## Основной принцип

**Каждый файл, функция и модуль должны иметь понятную причину своего существования.**

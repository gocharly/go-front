# Backend Architecture & Data Integrity

## Назначение

Backend отвечает за серверную логику приложения, работу с данными, авторизацию, внешние сервисы и выполнение операций, которые не должны выполняться непосредственно на клиенте.

Backend должен быть:
* понятным;
* предсказуемым;
* безопасным;
* тестируемым;
* устойчивым к ошибкам;
* соответствующим реальному размеру проекта.

Не создавать сложную серверную архитектуру без необходимости.

---

## Перед созданием backend

Определить:
* какие данные принимает система;
* какие данные возвращает;
* какие операции выполняются;
* где хранятся данные;
* какие пользователи имеют доступ;
* какие внешние API используются;
* какие операции требуют авторизации;
* какие операции могут выполняться долго;
* какие данные являются чувствительными;
* какие ошибки могут возникнуть.

После этого определить минимальную структуру backend.

---

## Основная структура

Типовая последовательность:

```text
Request
↓
Route
↓
Validation
↓
Authentication / Authorization
↓
Business logic
↓
Database / External API
↓
Response
```

Каждый этап должен иметь понятную ответственность.
Не помещать всю обработку запроса в один обработчик.

---

## Routes

Routes отвечают за определение endpoint и передачу запроса дальше.

```text
route
↓
service
↓
repository / integration
```

---

## Validation

Входные данные необходимо проверять до выполнения основной логики.

Проверять:
* обязательные поля;
* типы;
* формат;
* диапазоны;
* допустимые значения;
* размеры данных;
* связанные ограничения.

Нельзя доверять данным только потому, что клиент уже выполнил проверку.
Frontend validation улучшает интерфейс. Backend validation обеспечивает корректность и безопасность сервера.

---

## Business Logic

Основные правила приложения должны находиться в понятном месте:
`CreateOrder`, `CalculateOrderTotal`, `CancelOrder`, `RegisterUser`, `UpdateProfile`, `ProcessPayment`.

Названия должны отражать реальное действие.
Не создавать универсальный `Manager`, который содержит всю бизнес-логику проекта.

---

## Database & Transactions

Работу с базой отделять от бизнес-логики:
```text
Service → Repository → Database
```

Использовать транзакции там, где несколько операций должны выполниться как единое действие (`Create order + Create items + Update balance`).
При изменении схемы использовать миграции.

---

## Authentication & Passwords

Разделять:
* **Authentication** — кто пользователь.
* **Authorization** — что пользователь может делать.

Пароли хэшировать (bcrypt/argon2). Секреты хранить только в переменных окружения.

---

## Ошибки, API, Платежи & Webhooks

* API имеет четкий контракт, ошибки обрабатываются предсказуемо.
* Не возвращать клиенту stack trace и секреты.
* Внешние сервисы изолировать в `integrations/`.
* Платежи и webhook защищать от повторной обработки.
* Долгие задачи выносить в `Queue -> Worker`.
* Не использовать микросервисы и Redis по умолчанию без реальной необходимости.

# AI-кодинг и физический реализм архитектуры

Данный справочник объединяет практический опыт фронтирной AI-разработки (Т. Хахалев, Д. Киселев) и законы аппаратной производительности (С. Кушниренко @dalerank, П. Шерстнев).

---

## 1. Шесть фундаментальных законов AI-кодинга

### Закон 1: Субъектная ответственность инженера
* **Иллюзия:** «Агент пишет плохой код, нейросети еще сырые».
* **Реальность:** Фронтирные модели работают на уровне крепкого middle-разработчика. Сбой агента — это всегда сбой процесса, организованного человеком:
  1. **Грязный контекст:** перегружен лишними файлами или противоречивыми требованиями.
  2. **Абстрактные инструкции:** вместо директивного технического задания выданы размытые пожелания.
  3. **Отсутствие критериев приемки:** нет автотестов, агенту не предоставлен критерий «что считается успехом».

### Закон 2: Прогрев контекста «Сверху-Вниз» (Top-Down Priming)
* Никогда не бросать агента на отдельный баг в глубине неизвестного файла.
* **Правильный цикл:**
  `Архитектурная карта (Memory Bank / project-map.md) -> Подсистемы и связи -> Узкий срез целевого модуля`.
* В контекст подтягиваются только релевантные контракты и связанные интерфейсы.

### Закон 3: Абсолютная фиксация плана в Markdown
* Любая доработка начинается с составления и согласования единого `.md` плана.
* План обязан содержать:
  - Учет тонких моментов и граничных условий;
  - Ссылки на существующие соглашения проекта;
  - Пресечение оверинжиниринга (Senior Engineer Simplicity Test);
  - Закрытие всех пробелов (gaps) до начала написания кода.
* Пока у агента или инженера остаются вопросы — план не считается готовым.

### Закон 4: Тесты вместо человеческого Code Review
* Вычитывание тысяч строк машинного кода приводит к эффекту «замыливания глаза» — критические дефекты пропускаются.
* **Главный критерий приемки:** сквозной интеграционный e2e-тест сценария использования фичи.
* Агент обязан иметь возможность автономно запустить тесты для самопроверки (`Step -> Verify`).

### Закон 5: Протокол верификации «Не верь слову Готово»
* Когда модель рапортует об успешном завершении задачи, в 80% случаев остаются упущенные детали или нереализованные подпункты.
* **Обязательная процедура:** агент открывает исходный `.md` файл плана и построчно сопоставляет каждый пункт с реальным кодом:
  - `Пункт 1: DTO-валидация — РЕАЛИЗОВАНО (файл user.dto.ts, строки 14-28)`;
  - `Пункт 2: Индекс в БД — РЕАЛИЗОВАНО (миграция 004_add_idx.sql)`;
  - `Пункт 3: e2e-тест — ЗАКРЫТО (tests/auth.e2e.ts, тест пройден)`.

### Закон 6: Git-гигиена атомарных чекпоинтов
* Git — единственный инструмент детерминированного отката галлюцинаций модели:
  - План согласован -> `git commit`;
  - Шаг реализован и тесты зеленые -> `git commit`;
  - Рефакторинг завершен -> `git commit`.

## 2. Физика железа против догматичного «Clean Code» (Анти-ООП-слоп)

Текстовый нейрослоп засоряет внимание читателя; псевдо-«чистый код» засоряет процессорные кэши и время ожидания команды.

### 2.1. Иллюзия «комфорта за 10% скорости»
Многие разработчики оправдывают раздувание слоев абстракции словами: «Я готов пожертвовать 10% производительности ради читаемости».
В реальности эта сделка глубоко убыточна:
1. **Разрозненная куча аллокаций:** Иерархии объектов, завернутых в `shared_ptr` или сборщик мусора, раскиданы по оперативной памяти.
2. **Промахи кэша (Cache Misses):** При обходе графа объектов процессор простаивает сотни тактов, ожидая подгрузки данных из медленной RAM.
3. **Виртуальные вызовы убивают компилятор:** Полиморфизм на каждый чих блокирует инлайнинг функций, ломает Branch Prediction Unit и делает невозможной векторизацию циклов (SIMD).

### 2.2. Data-Oriented Design (DOD): Данные первичны
* Вместо графа объектов с методами («сущность знает, как себя обновлять») код строится на **плоских массивах данных** (Structure of Arrays — SoA):
  ```text
  // ПЛОХО (ООП-слоп): каждый объект в своей памяти, виртуальный прыжок на каждый шаг
  for (Entity* e : scene.getAll()) {
      e->getTransform()->update(dt);
  }

  // ХОРОШО (Data-Oriented): данные лежат непрерывным блоком, компилятор векторизует
  for (size_t i = 0; i < count; ++i) {
      positions[i] += velocities[i] * dt;
  }
  ```
* Плоский код без лишних слоев проще читать, проще профилировать и он в разы быстрее на реальном железе.

### 2.3. Закон распространения тормозов по сети зависимостей
* Программист запускает свой код сотни раз за день (правка -> сборка -> запуск -> отладка).
* Замедление инкрементальной сборки на 1 секунду (тяжелый заголовочный файл) при 60 сборках в день сжигает часы рабочего времени.
* В команде тормоза умножаются на каждом стыке:
  ```text
  Замедление тулзы с 0.2с до 8с
    × 40 генераций ассетов в день
    × 40 специалистов команды
    = +4 ЧАСА ОЖИДАНИЯ В ДЕНЬ В ПУСТОТУ
  ```

### 2.4. Единый домен времени
Не существует разделения на «микросекунды системщиков и секунды пользователей».
В realtime-системах (60 fps = 16.6 мс на кадр):
* Рендер: 4.0 мс
* Физика: 3.0 мс
* Анимация: 2.0 мс
* Логика: 5.6 мс
* **Запас: всего 2.0 мс**
Если «красивая» абстракция добавила 0.0008 мс на сущность при 30 000 сущностей — это **+2.4 мс**. Запас пробит, кадр дропнут, игра зависла.

## 3. RAG-гигиена и архитектура контекста

1. **AST-чанкование против слепого текстового сплиттинга:**
   - Разбивка кода по 800 символов разрывает сигнатуры, тела функций и области видимости.
   - Чанкование кода обязано следовать AST-структуре: файл, модуль, класс, изолированная функция.
2. **Advanced RAG: Ранжирование и отсечение дубликатов:**
   - Перед подачей найденных фрагментов модели обязателен этап реранкинга (Rerank) и удаления пересекающихся чанков. Контекстное окно очищается от паразитного шума.

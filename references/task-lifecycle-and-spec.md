# Жизненный цикл задачи и стандарт спецификации (spec.md)

Модульный регламент сквозного ведения задач от сбора требований до сдачи. Гарантирует воспроизводимость работы и сохранность контекста при сжатии истории, смене сессий и возвращении к проекту через время.

---

## 1. Главный принцип и цель

**Работа обязана быть полностью воспроизводимой без истории чата.**

Если новый агент или новая сессия получает только:
```text
SKILL.md
spec.md
memory_front.md
```
он обязан сразу понимать:
* что необходимо сделать;
* зачем это нужно;
* какие требования зафиксированы;
* что уже сделано;
* что сейчас в работе;
* какие решения были приняты;
* какие ограничения действуют;
* где остановилась предыдущая сессия;
* какое конкретное действие выполнять следующим.

Нельзя начинать полноценную реализацию сложной задачи, пока требования не собраны и не зафиксированы в `spec.md`. Если запрос простой и однозначный - задача выполняется сразу без лишней бюрократии.

---

## 2. Сквозной конвейер задачи

```text
ЗАПРОС ПОЛЬЗОВАТЕЛЯ
        ↓
АНАЛИЗ И ДИАГНОСТИКА ПЕРВОПРИЧИНЫ (Root Cause Investigation)
        ↓
ДОКЛАД ПОЛЬЗОВАТЕЛЮ И СОГЛАСОВАНИЕ (Mandatory User Approval Gate)
        ↓
ВОПРОСЫ / УТОЧНЕНИЯ (если есть неопределенность)
        ↓
СОЗДАНИЕ / ОБНОВЛЕНИЕ spec.md (для комплексных задач)
        ↓
ПОШАГОВЫЙ ПЛАН
        ↓
ХИРУРГИЧЕСКАЯ РЕАЛИЗАЦИЯ
        ↓
ПРОВЕРКА КАЖДОГО ШАГА
        ↓
ОБНОВЛЕНИЕ ПРОГРЕССА (spec.md)
        ↓
ФИНАЛЬНАЯ ПРОВЕРКА ПО ВСЕМ ПУНКТАМ
        ↓
ИТОГОВЫЙ ОТЧЕТ
```

При сжатии контекста или переходе в новую сессию:
```text
СЖАТИЕ КОНТЕКСТА / СБРОС
        ↓
ФИКСАЦИЯ memory_front.md
        ↓
ОБНОВЛЕНИЕ spec.md (Current State + Next Action)
        ↓
НОВАЯ СЕССИЯ (/new)
        ↓
ЧТЕНИЕ SKILL.md -> spec.md -> memory_front.md
        ↓
БЫСТРОЕ ВОССТАНОВЛЕНИЕ ТОЧКИ РАБОТЫ
        ↓
ПРОДОЛЖЕНИЕ С NEXT ACTION
```

## 3. Сбор требований и правила вопросов

1. **Анализ на входе**:
   * Что именно хочет пользователь.
   * Насколько задача масштабна.
   * Есть ли неоднозначности или технические развилки.
   * Какие требования уже известны (информация из запроса считается известной, переспрашивать ее запрещено).
   * Нужны ли уточнения перед стартом.

2. **Конкретные вопросы**:
   * Задавать вопросы только для устранения конкретной неопределенности.
   * Не задавать вопросы ради вопросов.
   * Не спрашивать 20 пунктов там, где хватает 3 целевых вопросов.
   * Пример фокусных вопросов:
     - Какой конкретный результат ожидается на выходе?
     - Какие функции строго обязательны, а что вторично?
     - Есть ли жесткие ограничения по стеку или зависимостям?
     - Какие существующие модули/экраны должны остаться нетронутыми?
     - Есть ли визуальный референс или конкретный стиль?

3. **Последовательное уточнение**:
   * Если ответ пользователя порождает новую развилку, задается короткий уточняющий блок.
   * Не пытаться предугадать абсолютно все на 10 шагов вперед.
   * Как только информации достаточно - агент прекращает опрос и переходит к формированию `spec.md`.

## 4. Эталонная структура spec.md

Файл `spec.md` создается в корне проекта и служит живым источником правды:

```markdown
# Specification

## 1. Goal
Что необходимо получить в результате.

## 2. User Requirements
Требования пользователя.
- [ ] Требование 1
- [ ] Требование 2

## 3. Functional Requirements
Что система должна делать.
- [ ] Функция 1
- [ ] Функция 2

## 4. UI / UX Requirements
Интерфейсные и визуальные требования.
- [ ] Требование 1
- [ ] Требование 2

## 5. Technical Requirements
Технологии, архитектура, ограничения и технические решения.

## 6. Constraints
Что нельзя делать.
- Не изменять ...
- Не добавлять ...
- Не использовать ...

## 7. Architecture
Структура файлов, компонентов и распределение ответственности.

## 8. Implementation Plan
Пошаговый план реализации.
- [ ] Шаг 1
- [ ] Шаг 2
- [ ] Шаг 3

## 9. Progress
Текущий прогресс.

### Completed
- [x] Выполненный пункт

### In Progress
- Пункт в работе

### Remaining
- [ ] Оставшийся пункт

## 10. Decisions
Принятые архитектурные и продуктовые решения.

| Date | Decision | Reason |
|---|---|---|
| YYYY-MM-DD | Суть решения | Причина и влияние |

## 11. Work Log
История работы по шагам.

### YYYY-MM-DD HH:MM
- Выполнено: ...
- Изменено: ...
- Проверено: ...
- Следующий шаг: ...

## 12. Current State
Где именно работа остановилась в текущий момент.

## 13. Next Action
Какое конкретное действие необходимо выполнить следующим.

## 14. Verification
Что уже проверено и работает.
- [ ] Сборка (Build)
- [ ] Тесты (Tests)
- [ ] Интерфейс (UI)
- [ ] Адаптивность (Responsive)
- [ ] Функционал (Behavior)
- [ ] Соответствие требованиям (Requirements)

## 15. Tests (TDD)
### Test Cases
- [ ] Проверить основной сценарий
- [ ] Проверить ошибочный сценарий
- [ ] Проверить граничный случай

### TDD Status
RED / GREEN

### Verification Log
- YYYY-MM-DD HH:MM - тест создан, RED
- YYYY-MM-DD HH:MM - реализация добавлена
- YYYY-MM-DD HH:MM - тесты GREEN

## 16. Final Result
Заполняется строго после полного завершения задачи.
```

## 5. Правила ведения и актуализации spec.md

1. **spec.md - живой документ**:
   Он обязан отражать фактическое положение дел в коде в любой момент времени, а не оставаться памятником первому диалогу.
2. **Запрет ложных отметок**:
   Категорически запрещено ставить `[x]`, если пункт фактически еще не написан или не проверен. Галочка ставится строго по факту верификации.
3. **Обновление после каждого значимого шага**:
   Не ждать завершения всей большой фичи. Сделан модуль -> записать в Work Log, обновить checkbox, обновить `Current State` и `Next Action`.
4. **Реакция на смену требований**:
   Если пользователь изменил вводные:
   - Зафиксировать изменение в `Decisions` (с датой, причиной и влиянием на проект).
   - Актуализировать пункты плана и требований в `spec.md`.
   - Переоценить выполненный код и продолжить по новой спецификации.

## 6. Оперативная память сессии (memory_front.md)

Для длинных задач используется легкий файл оперативного состояния:
`memory_front.md`

Он фиксирует срез текущей сессии:

```markdown
# Session Memory

## Current Task
Краткое описание текущей подзадачи.

## What Was Done
- Пункт 1
- Пункт 2

## Current Work
Что делается прямо сейчас.

## Last Change
Последнее изменение в кодовой базе.

## Problems
Встреченные проблемы и блокеры.

## Decisions
Локальные решения текущей сессии.

## Next Step
Точный следующий шаг.

## Files Changed
- путь/к/файлу1
- путь/к/файлу2
```

**Разделение ролей**:
* `spec.md` - долгосрочная спецификация всей задачи со всеми требованиями, планом и логом.
* `memory_front.md` - оперативный снимок текущей рабочей сессии перед перезапуском или сжатием.

## 7. Pre-Action Check перед каждым действием

Перед любым существенным изменением файлов агент проводит внутренний чек-лист:
- [ ] Я точно понимаю, что именно попросил пользователь?
- [ ] Это изменение прямо следует из `spec.md`?
- [ ] Я не добавляю ничего лишнего, о чем пользователь не просил?
- [ ] Я не нарушаю существующие ограничения проекта?
- [ ] Я понимаю архитектурное место этого изменения?
- [ ] Я знаю, какой конкретно шаг плана сейчас закрываю?

Если хотя бы на один пункт ответ "нет" - сначала устранить неопределенность, и только затем трогать файлы.

## 8. Проверка соответствия и финальный отчет

Перед объявлением задачи выполненной агент проходит `spec.md` сверху вниз:
- Проверено ли каждое требование пользователя?
- Работает ли каждая заявленная функция?
- Не нарушены ли ограничения?
- Проверен ли интерфейс и адаптивность?
- Проверена ли сборка и отсутствие ошибок?

Финальный раздел `Final Result`:
* Если все требования закрыты и проверены -> `Status: Completed`.
* Если часть задач осталась или требует действий со стороны пользователя -> `Status: Partial` с явным списком остатка. Запрещено ставить статус завершенности при наличии нерешенных пунктов.

## 9. TDD - тесты до реализации

### Цель
Использовать тесты как точные и однозначные критерии выполнения задачи.
Если функционал допускает автоматическое тестирование, агент формулирует тестовые сценарии **до реализации основного кода**. Тест описывает ожидаемое внешнее поведение системы, а не детали внутренней реализации.

### Рабочий цикл TDD
```text
ОПРЕДЕЛИТЬ ПОВЕДЕНИЕ
        ↓
СОЗДАТЬ ТЕСТ
        ↓
RED (убедиться, что тест падает)
        ↓
РЕАЛИЗОВАТЬ ТОЛЬКО НЕОБХОДИМЫЙ КОД
        ↓
GREEN (убедиться, что тест проходит)
        ↓
ПРОВЕРИТЬ ГРАНИЧНЫЕ СЛУЧАИ
        ↓
ИСПРАВИТЬ НАЙДЕННЫЕ ОШИБКИ
        ↓
ПОВТОРНО ЗАПУСТИТЬ ТЕСТЫ
```

### Правила TDD
* Тест обязан проверять конкретное требование из `spec.md`.
* Исходно тест обязан падать (RED), доказывая отсутствие реализации.
* Агент реализует ровно столько кода, сколько требуется для прохождения теста.
* При ошибке агент сначала читает фактический вывод теста, затем точечно устраняет причину.
* Задача не считается закрытой, пока тесты не стали зелеными (GREEN).
* Если для конкретной задачи автоматический тест не имеет практического смысла (например, визуальная правка отступа), агент не выдумывает искусственные тесты ради формализма.

### Матрица типов проверок
```text
Backend / Бизнес-логика  ->  Unit / Integration tests
API эндпоинты            ->  Request / Response contract tests
База данных / Хранилище  ->  Data Layer integration tests
Пользовательский UI      ->  Visual / Interaction inspection
Сборка проекта           ->  Build verification (tsc, vite build)
Конфигурация             ->  Schema validation
```

## 10. Оркестратор и распределение задач

### Цель
Использовать нескольких агентов строго тогда, когда задача объективно делится на независимые части. Оркестратор - главный координатор работы. Он не обязан писать весь код сам.

### Критерии применения оркестрации
Оркестрация применяется, если:
* задача крупная;
* части работы изолированы и независимы;
* параллельная работа реально экономит время;
* результаты можно независимо проверить.

Для небольших и линейных задач используется строго один агент. **Запрещено плодить мультиагентность ради самой мультиагентности.**

### Роль оркестратора
1. Анализ задачи и чтение `spec.md`.
2. Декомпозиция на изолированные подзадачи.
3. Передача исчерпывающего контекста (Task, Goal, Requirements, Constraints, Scope, Verification).
4. Контроль исполнения и проверка результатов.
5. Объединение изменений и финальный аудит проекта.

```text
                    ORCHESTRATOR
                         │
          ┌──────────────┼──────────────┐
          ↓              ↓              ↓
       Backend           UI           Tests
          │              │              │
          └──────────────┼──────────────┘
                         ↓
                    Verification
                         ↓
                       Merge
```

### Правило жестких границ (Scope Boundary)
Дочерний агент работает строго в пределах переданного контракта. Ему **категорически запрещено** самостоятельно расширять scope. Если в процессе работы вскрылась проблема в другой части системы:
```text
ОБНАРУЖЕНА СМЕЖНАЯ ПРОБЛЕМА
        ↓
ЗАФИКСИРОВАТЬ В ОТЧЕТЕ
        ↓
СООБЩИТЬ ОРКЕСТРАТОРУ
        ↓
ОРКЕСТРАТОР РЕШАЕТ, ВКЛЮЧАТЬ ЛИ В ПЛАН
```

Дочерний агент не возвращает сухое "Done". Он сдает отчет:
* что выполнено;
* измененные файлы;
* результаты тестов;
* возникшие проблемы;
* оставшаяся работа.

## 11. Изоляция через Git Worktrees

### Цель
Изолировать независимую работу агентов друг от друга и от основной рабочей версии проекта. Каждая независимая задача выполняется в отдельном Git worktree:

```text
project/
│
├── main
│
├── worktree-auth
├── worktree-ui
└── worktree-tests
```

### Рабочий цикл с Worktree
```text
СОЗДАТЬ ПОДЗАДАЧУ
        ↓
СОЗДАТЬ ВЕТКУ (git branch)
        ↓
СОЗДАТЬ WORKTREE (git worktree add)
        ↓
ПЕРЕДАТЬ ЗАДАЧУ АГЕНТУ
        ↓
РЕАЛИЗАЦИЯ И ТЕСТЫ В WORKTREE
        ↓
КОММИТ
        ↓
РЕВЬЮ И ПРОВЕРКА СООТВЕТСТВИЯ
        ↓
СЛИЯНИЕ В ОСНОВНУЮ ВЕТКУ (Merge)
```

Агент в worktree не имеет права напрямую коммитить в основную ветку.

### Чек-лист проверки перед Merge
Перед объединением оркестратор проверяет:
- [ ] Изменения строго соответствуют `spec.md`
- [ ] Scope не был самовольно расширен
- [ ] Нет лишнего кода и мусорных файлов
- [ ] Все тесты проходят (GREEN)
- [ ] Сборка проекта проходит без ошибок
- [ ] Архитектура не нарушена
- [ ] Изменены только необходимые файлы

## 12. Связь механизмов и матрица ответственности

TDD, оркестратор, worktrees и память работают как единый конвейер:

```text
                    SPEC.md
                       │
                       ▼
                 ORCHESTRATOR
                       │
             ┌─────────┼─────────┐
             ↓         ↓         ↓
          Agent A   Agent B   Agent C
             │         │         │
             ▼         ▼         ▼
         Worktree   Worktree   Worktree
             │         │         │
             ▼         ▼         ▼
           Tests     Tests     Tests
             │         │         │
             └─────────┼─────────┘
                       │
                       ▼
                  Verification
                       │
                       ▼
                     Review
                       │
                       ▼
                     Merge
                       │
                       ▼
                 Update spec.md
                       │
                       ▼
                 Update Progress
```

### Матрица ответственности
* **`spec.md`** - что именно необходимо сделать (требования, ограничения, архитектура, план, статус).
* **TDD** - как доказать и проверить, что функционал работает корректно.
* **Оркестратор** - кто, в какой последовательности и в каких границах выполняет работу.
* **Git worktree** - где физически и изолированно выполняются изменения.
* **`memory_front.md`** - где именно остановилась текущая рабочая сессия.
* **Work Log** - что конкретно происходило по минутам во время работы.

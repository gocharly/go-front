# GO-FRONT

Единый архитектурный стандарт разработки, текстовой инженерии и визуальной эргономики для AI-агентов.

Стандарт гарантирует полную воспроизводимость работы при сжатии контекста, сбросе сессий (`/new`) или передаче задачи другому агенту по цепочке:
`SKILL.md` -> `spec.md` -> `memory_front.md`

---

## Установка и подключение

### Через npx / npm
```bash
npx @gocharly/go-front -g
```

### Прямое подключение в проект
Клонируйте репозиторий в каталог навыков агента:
```bash
git clone https://github.com/gocharly/go-front.git ~/.agents/skills/go-front
```

## 1. Базовые правила разработки (Core Development Rules)

Обязательны для каждой задачи без исключений:

1. **Только то, что попросили**: категорический запрет добавлять отсебятину - декорации, свечения (glow), случайные градиенты, точки, линии, анимации, непрошеные кнопки, страницы или текст. Если элемент не просили - не добавлять. Чужой код вне задачи не трогать.
2. **Никакого мусора (Anti-Slop)**: пустое пространство - естественная часть дизайна. Запрещено заполнять экран элементами "для красоты" или "чтобы не было пусто".
3. **Названия по реальному функционалу**: строгий запрет на абстрактные имена (`Helper`, `Manager`, `Utils`, `Handler`, `Stuff`). Имя обязано прямо описывать действие (`PaymentCalculator`, `UserProfile`, `ChatHistory`).
4. **Структура без оверинжиниринга**: разделение по реальной ответственности, вынос повторной логики, запрет создания абстракций "впрок".
5. **Фильтр перед созданием**: 5 контрольных вопросов перед добавлением любого элемента (требуется ли задачей, необходимо ли для работы, конкретна ли ответственность, понятно ли имя, нет ли уже готового решения).
6. **Выходной контроль**: обязательная сверка diff перед сдачей на отсутствие лишнего кода.

Главный принцип: **Сначала понять задачу -> сделать ровно необходимое -> не добавлять ничего сверху -> проверить результат.**

## 2. Жизненный цикл задачи и память сессий

### Живая спецификация (spec.md)
Для каждой существенной задачи в корне проекта создается и непрерывно ведется `spec.md` - единственный живой источник правды:
- **16 обязательных разделов**: Goal, User Requirements, Functional Requirements, UI/UX Requirements, Technical Requirements, Constraints, Architecture, Implementation Plan, Progress, Decisions, Work Log, Current State, Next Action, Verification, Tests (TDD), Final Result.
- **Запрет ложных отметок**: запрещено ставить `[x]`, пока пункт фактически не реализован и не проверен.
- **Фиксация смены требований**: любые изменения ТЗ немедленно фиксируются в таблице `Decisions` с указанием даты, причины и влияния на код.

### Оперативная память сессии (memory_front.md)
Легкий моментальный снимок текущей рабочей сессии для безопасного перехода между диалогами (`/new`):
- Содержит: `Current Task`, `What Was Done`, `Current Work`, `Last Change`, `Problems`, `Decisions`, `Next Step`, `Files Changed`.
- `spec.md` хранит спецификацию всей задачи, а `memory_front.md` - оперативную точку текущей сессии.

### TDD - тесты до реализации
- Поведение системы описывается тестом до написания кода.
- Рабочий цикл: `Поведение -> Тест -> RED -> Минимальный код -> GREEN -> Проверка граничных случаев`.
- Статусы проверок фиксируются прямо в блоке `Tests (TDD)` файла `spec.md`.

## 3. Мультиагентность и параллелизация

### Рой агентов (Swarm Protocol)
Децентрализованный протокол параллельной разработки несколькими агентами в общем рабочем пространстве без жесткого центрального планировщика:
- **Фаза 1: Координация (Правки кода запрещены)**: агенты заявляют зоны ответственности, перечни файлов и TypeScript-контракты. Пересечения разрешаются до начала кодинга.
- **Фаза 2: Реализация**: агенты пишут код строго в пределах своих закрепленных файлов, не трогая чужие модули.
- **Фаза 3: Синхронизация и догон**: вычитка входящих сообщений, адаптация под актуальные решения напарников и локальная верификация.
- **Статус решений `[DECISION]`**: ключевые интерфейсы и контракты помечаются префиксом `[DECISION]` и обязательны для всей команды роя.
- **Правило тишины (Zero Noise)**: категорический запрет статусного шума ("принял", "согласен", "закончил"). Коммуникация ведется только по существу.

### Оркестратор и Git Worktrees
- Оркестратор декомпозирует задачу и передает дочерним агентам жесткий контракт без права расширения scope.
- Независимые ветки физически изолируются в отдельных директориях через Git Worktrees (`worktree-auth`, `worktree-ui`).
- Прямые коммиты в основную ветку из worktree запрещены.

## 4. Визуальная гигиена и верстка

- **Запрет прыгающих анимаций**: при появлении элементов по скроллу категорически запрещены вертикальные скачки и смещения (`y`, `translateY`). Появление блоков происходит строго на месте через прозрачность (`opacity: 0 -> 1`).
- **Чистота центра и контактов**: в блоках контактов и CTA запрещено перекрывать текст и кнопки линиями, петлями и стрелками. Центр обязан оставаться чистым; декорации выносятся на фланги.
- **Зазоры в сетках**: расстояние между карточками и блоками - от 32-40px (gap-8+) во избежание визуального слипания.
- **Привязка декора**: ярлыки и стикеры фиксируются прямо на углах контейнеров, а не висят в воздухе.
- **Запрет выдуманных лозунгов**: запрещено выдумывать слоганы и лепить на сайты искусственные лозунги (вроде "zero bloat") или выводить фразы об ограничениях.

## 5. Механический контроль качества (scan_slop.py)

В состав стандарта входит автономный скрипт-линтер:
`scripts/scan_slop.py`

### Команды
- Внутренняя проверка текста из stdin:
  ```bash
  echo "текст" | python3 scripts/scan_slop.py -
  ```
- Аудит файла на чистоту текста:
  ```bash
  python3 scripts/scan_slop.py path/to/file.md
  ```
- Автозамена типографики (дефисы, прямые кавычки, удаление эмодзи):
  ```bash
  python3 scripts/scan_slop.py path/to/file.md --fix
  ```
